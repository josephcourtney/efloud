## 1. Test taxonomy and markers

### 1.1 Scope markers

Every test **must** declare at least one of the following scope markers:

- `unit` — isolated, fast tests of pure or mostly pure logic
- `component` — tests of a coherent subsystem via its public API
- `integration` — tests involving real external dependencies
- `system` — end-to-end, black-box tests of critical workflows
- `contract` — tests of API, schema, or interface contracts

Scope semantics and design rules are defined in the L3 procedures.

### 1.2 Cross-cutting markers

Additional markers may be applied to express purpose or characteristics:

- `db` — touches a real database engine
- `slow` — noticeably slower than typical unit tests
- `smoke` — small, critical-path gating tests
- `regression` — guards against a previously observed defect
- `property_based` — uses property-based testing (e.g. Hypothesis)
- `observability` — asserts on logs, metrics, or traces
- `security`, `performance`, `data_quality`, etc., as needed

Markers are **strictly enforced**; unknown markers cause test failure.

---

### 1.3 Harness placement

Harness-related modules follow the same scope-marker rules but also rely on a predictable directory layout:

- **Harness helpers plus unit tests** live under `tests/harness/` and `tests/unit/`. These modules exercise the harness APIs directly and all carry `pytest.mark.unit`.
- **Harness case execution** (manifests, dictionaries, runners) belongs under `tests/integration/`. These modules typically touch actual CIF files and run via `pytest.mark.integration`; those needing vendor data also add `pytest.mark.external_data`.
- **Vendor/IUCr suites** remain in `tests/external/`, carry `pytest.mark.external_data` (and `pytest.mark.slow` because they pull large archives), and skip with `REPO_HINT` when the vendor files are absent; they may migrate into the harness only after the tooling has stabilized.

Keeping this placement ensures marker-driven `just test-marker` commands stay predictable and keeps harness code logically organized.


## 2. Directory layout (conventional)

All tests live under the top-level `tests/` directory.

Recommended structure:

```text
tests/
  unit/
  component/
  integration/
  system/
  property/
  data/          # static test fixtures (JSON, YAML, HTML, etc.)
```

Notes:

* Directory placement does not replace scope markers; markers remain authoritative.
* Property-based tests may live under `tests/property/` for clarity.
* Large or reusable fixtures should live in `tests/data/` or be generated by fixtures.

## 3. Pytest configuration and enforcement

### 3.1 Baseline configuration

Pytest is the standard test runner. The repository enforces strict configuration.

Example (`pyproject.toml` or `pytest.ini`):

```toml
[tool.pytest.ini_options]
  minversion = "8.0"
  testpaths = ["tests"]
  python_files = ["test_*.py"]

  addopts = [
    "--strict-markers",
    "--strict-config",
    "-ra",
    "--cov=your_package_name",
    "--cov-branch",
    "--cov-report=xml",
  ]

  xfail_strict = true

  log_cli = true
  log_cli_level = "INFO"
  log_cli_format = "%(asctime)s [%(levelname)s] %(name)s - %(message)s"
  log_cli_date_format = "%Y-%m-%d %H:%M:%S"

  filterwarnings = [
    "error::DeprecationWarning:your_package_name\\.",
    "ignore::DeprecationWarning:some_known_third_party",
  ]
```

### 3.2 Enforcement rules

* Unknown markers **fail** the test run (`--strict-markers`)
* Unknown config keys **fail** the test run (`--strict-config`)
* `xfail` is strict: an unexpected pass is a failure
* Deprecation warnings from the main package are treated as errors

## 4. Coverage reporting

* Branch coverage is enabled (`--cov-branch`)
* XML coverage reports are generated for CI
* Coverage thresholds (`fail_under`) may be enabled once a stable baseline exists

Example:

```toml
[tool.coverage.run]
  source   = ["your_package_name"]
  branch   = true
  parallel = true

[tool.coverage.report]
  show_missing = false
  skip_covered = true
  # Optional:
  # fail_under = 80
```

Coverage **targets and interpretation** are defined in `notes/testing/automated_testing.md` and enforced via phase procedures where applicable.

## 5. Standard commands

Projects **must** provide ergonomic commands (via `Makefile`, `justfile`, or scripts) so developers do not need to remember complex pytest expressions.

Recommended minimum targets:

```make
test-fast:
	pytest -m "not slow"

test-all:
	pytest

test:
	pytest

check:
	ruff check your_package_name tests
	mypy your_package_name tests
	pytest
```

Semantics:

* `test-fast`: developer loop (excludes known slow tests)
* `test`: CI-equivalent default
* `test-all`: full suite
* `check`: static analysis + tests (pre-commit / CI gate)

## 6. Recommended testing cadence

Suggested mapping from workflow events to commands:

| Trigger      | Command / selection                                      | Expected duration |
| ------------ | -------------------------------------------------------- | ----------------- |
| Every save   | `pytest tests/unit -q`                                   | < 5 s             |
| Every commit | `pytest -m "unit and not slow" -q`                       | ≤ 2 min           |
| Pull request | `pytest -m "unit or component or contract and not slow"` | ≤ 10–15 min       |
| Nightly      | `pytest` (full suite incl. slow/system/integration)      | up to ~60 min     |
| Pre-release  | Nightly + `-m "performance or security or data_quality"` | project-specific  |

Exact budgets may vary, but the **fast → broad → exhaustive** pattern should be preserved.

## 7. Static analysis and security checks (mandatory)

On every commit and pull request, CI **must** run:

* Formatter (e.g. `ruff format`, `black`)
* Linter (e.g. `ruff check`)
* Type checker (e.g. `mypy`, `pyright`)
* Dependency vulnerability scanner (e.g. `pip-audit`, platform SCA)
* Secret scanner (e.g. `gitleaks`, `trufflehog`)

CI **must fail** on:

* lint or type errors
* untriaged high/critical security findings
* detected secrets

Waivers or suppressions require explicit documentation and review.

## 9. Compliance evidence for L2-P2

The most recent testing audit (STATUS.md, section "Testing policy audit (2026/01/12)") targets the L2-P2 phase, which mandates **unit** and **component** coverage plus optional conditional/advisory tests. The repository currently satisfies those requirements as follows:

* **Unit tests** live under `tests/unit/` and, thanks to the compliance drive documented in TODO.md, every module now declares `pytestmark = pytest.mark.unit`. Marker-driven runners such as `just test-fast` (`pytest -m "unit and not slow"`) collect the full suite (83 tests executed on 2026-01-12) and confirm the scope is enforced.
* **Component tests** live under `tests/component/` and each module defines `pytestmark = pytest.mark.component`. Running `just test-marker "component"` confirms the component suite loads (3 tests executed on 2026-01-12), which together with the unit suite fulfills the L2-P2 mandatory classes.
* **Conditional/advisory tests** (regression, contract, etc.) are tracked via explicit markers when they exist. For now the suite has no regression- or contract-marked modules, so any future additions must introduce the appropriate `pytestmark = pytest.mark.regression` / `pytest.mark.contract` at the module level and be referenced by the corresponding `just test-marker "<marker>"` commands. The `notes/testing/L3_T5_regression.md` and `notes/testing/L3_T7_contract.md` procedures describe how to evaluate those classes when they are introduced.

Maintaining this section (and updating TODO.md when scope markers change) provides a single place for auditors to verify coverage and marker-driven command behavior.

## 10. Support data & harness infrastructure

* `tests/support_data/` now hosts fixtures, dictionaries, vendor suites, corpora, and manifests with a README, the `tests.support_data.support_data_path` helper, and updated fetch tooling to resolve every manifest-driven suite into that documented location.
* `tests/support_data/cif_builders.py` exposes deterministic CIF block/loop/item helpers, and unit/component/system/formatter/validator/diff suites all import them so newline/whitespace behavior stays consistent across fixtures instead of relying on ad-hoc literals.
* `tests/support_data/fetch_resources.py` now normalizes `ciftestN` files lacking a `.cif` suffix before directory creation so the IUCr archives can be fetched without collisions, and manifest hooks (`mmcif_dict_cases.json`, `grammar_cases.json`, `iucr_vendor_cases.json`) route through `tests/integration/test_harness_manifests.py` so dictionary/dialect/fix/grammar coverage plus IUCr vendor gating reuse the same loader/runner and skip/failure messaging.
* The `tests/harness/` package (loader, invariants, expectations, runner) plus `tests/integration/test_harness_manifests.py` and `tests/integration/test_coverage_smoke.py` exercise manifest-driven cases, dictionary resolution, invariant assertions, and optional fix verification without touching existing CLI flows, keeping the harness core focused on deterministic validators and fix handling.
* The fix-case manifest, no-op round-trip samples, harness report, and coverage smoke test (`tests/support_data/manifests/fix_cases.json`, `tests/support_data/fixtures/cases/roundtrip/*`, `tests/harness/report.py`, `tests/integration/test_coverage_smoke.py`, `tests/.artifacts/`) have been validated via `just test-marker "integration"`.
* `tests/external/test_conformance_suites.py` wraps `tests/external/conformance.py` so the `ciftest2` and `iucr-trip` suites reuse the same manifest loader, strict-finding helper, and `external_data` gating, preserving the `REPO_HINT` messaging when vendor data is absent.
