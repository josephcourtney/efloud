# Testing Procedure

## Level L1 — Project Lifecycle Testing Procedure

### Purpose and scope

This procedure governs **when** different categories of testing are required across the project lifecycle and **which phase-scoped procedures must be invoked** at any given time.

It does **not** define how to write tests, how to configure tooling, or how to evaluate individual test quality. Those concerns are delegated to lower-level procedures.

This procedure applies continuously throughout the life of a project and is re-entered whenever:

* the project changes lifecycle phase,
* a release decision is made, or
* a material change is proposed (feature, refactor, dependency, infrastructure).

### Re-entry triggers (definition of “material change”)

Re-enter this procedure whenever a change:

* affects externally visible behavior (user-facing outputs, API responses, CLI output, persisted artifacts),
* alters an integration boundary (DB, HTTP, message bus, filesystem, authN/Z, identity, secrets, config),
* modifies data persistence, schemas, migrations, or data retention semantics,
* changes security-, performance-, availability-, or correctness-critical logic,
* upgrades runtime/platform dependencies with non-trivial behavioral risk (framework, ORM, HTTP client, crypto).

### State

Determine and record the following:

**Lifecycle Stage**: prototype | alpha | beta | production | maintenance
**Change Context**: new feature | refactor | bug fix | dependency upgrade | operational:config | operational:deployment | operational:scaling
**Risk Profile**: users:[internal | external], importance, constraints, impacts

### Routing
Based on the **Lifecycle Stage**, move to the appropriate level-2 procedure.

Note: multiple L2 procedures may apply for a single change (e.g., production hotfix during maintenance). If so, invoke all applicable L2 procedures and aggregate outcomes.

| **Lifecycle State** | **Primary Intent**                        | **Required L2 Phase Procedure(s)**                     | **Notes on Enforcement**                                               |
| ------------------- | ----------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------- |
| **Prototype**       | Explore feasibility; reduce uncertainty   | **L2-P1: Exploratory / Prototype Testing Phase**       | Tests mostly advisory; gaps acceptable if risks are documented         |
| **Alpha**           | Establish correctness of core behavior    | **L2-P2: Feature Development Testing Phase**           | Unit/component tests become gating for core logic                      |
| **Beta**            | Stabilize behavior; validate integrations | **L2-P3: Stabilization and Pre-Release Testing Phase** | Integration, contract, and smoke tests required for critical paths     |
| **Production**      | Ensure reliability and operability        | **L2-P4: Release and Hardening Testing Phase**         | Testing is a release gate; non-functional tests required as applicable |
| **Maintenance**     | Safely evolve a live system               | **L2-P5: Maintenance and Change Testing Phase**        | Regression coverage mandatory; new tests expected with changes         |

### Process

For each **L2 phase procedure**:

1. Execute the procedure in full.
2. Allow it to:

   * determine which test classes are required,
   * execute appropriate **L3 test-type procedures**,
   * assess compliance for its phase.
3. Collect its result:

   * pass,
   * conditional pass (with documented follow-ups),
   * fail.

### Aggregation and decision rules

After all required L2 procedures complete:

1. Aggregate outcomes.
2. Apply the following rules:

* **Any fail** → lifecycle progression or release is blocked.
* **Conditional pass only** → progression allowed only if conditions are explicitly accepted and tracked.
* **All pass** → progression allowed.

Decisions and rationale must be recorded (e.g., in release notes, change logs, or issue trackers).
